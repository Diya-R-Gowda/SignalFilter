## Technical Summary

One subsection per row of the status table above — what was actually built, the specific decisions made, and every real bug hit with its root cause and fix. Covers every `🟢 Done` and `🟡` row individually; `⚪ Not started` rows have no build to summarize yet and are left to their "Week 3+ idea" sections below instead.

### Define problem, architecture, tech stack

Core call: a hybrid two-stage pipeline (cheap embedding filter, then a local LLM for the real judgment) instead of either static keyword/sender rules (can't capture that "urgent" is relative to a focus that shifts hour to hour) or a single LLM call on every message (works, but pointlessly expensive when most messages are obviously off-topic). Storage is PostgreSQL via SQLAlchemy — chosen partly as deliberate Postgres practice, with the ORM layer making a future swap possible without a rewrite. Stage 1 uses `sentence-transformers`/`all-MiniLM-L6-v2`, local and free. Stage 2 uses Ollama running `qwen2.5:3b-instruct`, picked over `phi3:mini` specifically for better instruction-following and structured-JSON output — a real constraint given the dev machine is CPU-only inference (16GB RAM, Intel Iris Xe iGPU, no discrete GPU), which ruled out anything larger. Notifications use `win11toast`/`winsdk`, chosen explicitly over `win10toast` (unmaintained and flaky on modern Windows). Repo is a monorepo (`backend/`, `frontend/` added later); the frontend was deliberately deferred until the pipeline worked end-to-end via CLI, since a dashboard is only useful once there's real triage data to look at. Hard constraint carried through every choice above: nothing paid, no cloud resources anywhere in the stack.

### Install Postgres, create `signalfilter` DB

Standard installer, but hit a real problem immediately: the `postgres` user's password wasn't usable for the fresh install. Fixed via a documented recovery procedure rather than a reinstall — open an elevated PowerShell, edit `pg_hba.conf` to temporarily set the `local`/`host` auth methods to `trust` instead of `scram-sha-256`, restart the Postgres service, run `ALTER USER postgres WITH PASSWORD '...'` via `psql`, then revert `pg_hba.conf` back and restart again. The database itself is a single `CREATE DATABASE signalfilter` via `psql`. This exact sequence is captured in `README.md`'s Setup section so it doesn't need re-deriving on a future machine.

### Install Ollama, pull `qwen2.5:3b-instruct`

`ollama pull qwen2.5:3b-instruct` — a ~1.9-2GB one-time download, confirmed present via `ollama list`. Runs CPU-only; there's no discrete GPU on the dev machine, which is the direct reason this specific model was chosen over larger instruction-tuned options (see "Define problem, architecture, tech stack" above) — it needed to be small enough to score a message in real time on CPU alone.

### Scaffold FastAPI backend + Python deps

`backend/` with its own venv. `requirements.txt` covers `fastapi`, `uvicorn[standard]`, `sqlalchemy`, `psycopg[binary]`, `python-dotenv`, `slack-bolt`, `sentence-transformers`, `requests`, `win11toast`, and `pydantic-settings` from the initial scaffold, plus `google-api-python-client`, `google-auth-httplib2`, and `google-auth-oauthlib` added later specifically for the Gmail connector. All of it installed cleanly on Python 3.14 with no version pinning needed.

### SQLAlchemy models: `Item`, `FocusState`, `Feedback`

Three models originally (a fourth, `SyncState`, was added later for connector cursors — see Gmail connector below), all under `backend/app/models/`. `Item` is the central table: `source` (`"slack"`/`"gmail"`), `sender`, `content`, `thread_id`, `source_timestamp`, plus the `focus_text` it was actually scored against — captured per-item, deliberately, so a historical item stays interpretable even after the focus has since changed — `embedding_score`/`passed_stage1`, `llm_score`/`llm_reason`, and `notified`. `FocusState` is deliberately append-only rather than a single mutable row: every focus change inserts a new row, and "current focus" is just "the most recently created one" (`get_current_focus_state()` orders by `created_at desc`, `limit 1`) — this gets a free history of focus changes over time with no extra modeling effort. `Feedback` is a simple foreign-keyed `thumbs_up` per item. All models use a string UUID primary key (`str(uuid.uuid4())`) rather than an auto-incrementing int, and every table is created via one `init_db()` call (`Base.metadata.create_all`) run automatically at CLI startup — no separate migration tooling exists or was needed at this scale.

### Embedding filter (stage 1)

`embedding.py`'s `passes_stage1()` computes cosine similarity (`sentence-transformers`/`all-MiniLM-L6-v2`, local, CPU) between the focus text and the item's content. The threshold was tuned twice against real Slack traffic, both times downward from its original, more conservative starting point: `0.25 → 0.05` after a live test showed a genuinely relevant message scoring only 0.070 cosine similarity while an irrelevant one scored higher, 0.097 — short conversational text simply doesn't order well against a longer focus string at this model's scale. Then `0.05 → 0.0` after a second live test showed a clearly-relevant message ("how is the ui components coming along?", focus: "testing Signal Filter's Slack triage pipeline") scoring just 0.017 and getting filtered before ever reaching the LLM, while a genuinely unrelated distractor ("can we play volleyball?") scored negative, -0.035. That negative-vs-positive split turned out to be the only reliable signal at this scale, so the final design only blocks actively anti-correlated (negative-similarity) messages at stage 1 and defers every real judgment call to stage 2, per the original two-stage design intent.

### LLM judgment (stage 2)

`llm.py`'s `score_item()` calls local Ollama (`qwen2.5:3b-instruct`) with a system prompt requesting structured JSON (`{"score": 0-10, "reason": "..."}`) and explicit scoring bands (0-1 unrelated, 2-3 tangential, 4-5 same-topic-casual, 6-8 same-topic-urgent, 9-10 blocking). The score is hard-clamped to `[0, 10]` in code (`max(0, min(10, score))`) regardless of what the model returns. Two additions came from live tuning after the initial build: `temperature` pinned to `0`, so the same message scores identically across runs instead of drifting between calls; and an explicit rule that automated/bulk/marketing mail always scores 0-1 regardless of keyword overlap with the focus — added after real Gmail marketing mail was scoring high enough to notify just because it happened to mention focus-adjacent words.

### Native Windows notifications

`notify.py`'s `send_notification()` is a thin one-line wrapper around `win11toast.toast(title, body, duration="short")`. The library choice itself (over `win10toast`) is covered under "Define problem, architecture, tech stack" above. The one real bug tied to this piece — `toast()` blocking until dismissed, creating a data-loss window — is a pipeline-orchestrator-level fix, not a change to this file; see Pipeline orchestrator below for the actual fix, since moving *when* the toast fires (not what it does) was the correct fix location.

### Pipeline orchestrator

`pipeline.py`'s `process_item()` is the single place every message from every source passes through: read current focus → stage 1 (embed + filter) → if passed, stage 2 (LLM score) → decide notify via a per-source threshold → persist the full record → fire notification if applicable. If no focus has been set yet, stage 1 is skipped outright (`passed_stage1=False`) rather than crashing on an empty focus string. Notify threshold is per-source, not global: Slack fires at `interrupt_score_threshold=4` (casual on-topic check-ins should still notify there, per an earlier explicit request), Gmail at a stricter `gmail_interrupt_score_threshold=7` (only clearly actionable/urgent mail) — added after real-world use showed Gmail was notifying on too much at the shared threshold. **Bug found and fixed:** `win11toast.toast()` blocks until the toast is dismissed or expires. It was originally called *before* `session.commit()`, so a process restart during an active toast (which happened repeatedly while iterating on other fixes) could kill the process mid-toast and lose the database record of a real notification entirely — the pipeline would "forget" it had ever decided to notify. Fixed by committing the triage decision first, then firing the toast on a separate `threading.Thread(daemon=True)`, so the notification can never block execution or be lost regardless of what happens to the toast itself afterward.

### Slack connector (Socket Mode)

`slack_connector.py` — Socket Mode, chosen specifically so no public URL/ngrok tunnel is needed for a personal single-workspace tool. **Bug found and fixed:** `SocketModeHandler.start()` internally registers a `SIGINT` handler, which only works when called from the main thread — this broke the instant Slack started running alongside Gmail on a background thread under `--source all`. Fixed by switching to `handler.connect()` plus a blocking `threading.Event().wait()`, which avoids touching signal handling entirely. A second, more serious bug in this same file — `App(token=...)` itself crashing the whole process at import time on a dead token — is covered in full under Graceful connector failure handling below, since the fix there reshaped how this file constructs its client.

### CLI (`focus` / `run`)

`cli.py`, argparse-based, two subcommands. `focus <text>` writes a new `FocusState` row. `run --source {slack,gmail,all}` (default `all`) starts the requested connector(s) — a single source runs synchronously in the main thread; more than one spins a `threading.Thread(daemon=True)` per connector and joins them all, so the pipeline can service both sources concurrently while still letting Ctrl+C in the main thread stop everything. `main()` also reconfigures stdout to UTF-8 with `errors="replace"` before anything else runs — this fix was added after the Gmail stuck-cursor bug (see Gmail connector below) traced back specifically to Windows' default `cp1252` console encoding being unable to print emoji/non-ASCII message content.

### Setup docs (root README + backend README)

`README.md` carries the full walkthrough for a fresh machine: a prerequisites table, step-by-step Postgres/Ollama/Python-venv/`.env`/Slack-app-creation instructions (down to the exact bot scopes and event subscriptions needed), a config-reference table documenting every `.env` tunable with its default and the reasoning behind that default, a troubleshooting section built from real issues actually hit during setup (stale PATH after an installer, first-embedding-call slowness, Windows symlink warnings from `huggingface_hub`, the CORS/"API unreachable" bug, missing Gmail credentials), and a project-structure tree. `backend/README.md` was deliberately trimmed down to a pointer back to the root README once the root doc became the canonical setup source, specifically to avoid two setup guides drifting out of sync with each other.

### Running live against real Slack traffic

The first genuine end-to-end validation of the whole pipeline, not just unit-level testing of each stage in isolation: a relevant real message ("can you check if the pipeline is working?") scored 8/10 and correctly fired a notification; an irrelevant one ("anyone up for lunch?") scored 3/10 and was correctly held back. This same live pass is what caught the stage-1 threshold problem — the original `0.25` threshold was filtering out even relevant short messages before they ever reached the LLM (see Embedding filter (stage 1) above for the exact scores and the full threshold-tuning history down to `0.0`).

### FastAPI HTTP API (`/items`, `/focus`, `/items/{id}/feedback`)

`main.py` + `schemas.py` — thin wrappers over already-existing service functions, no new business logic: `GET`/`POST /focus` (delegates straight to `services/focus.py`), `GET /items` (source/notified filters, pagination capped at 100 to avoid an unbounded query), `POST /items/{id}/feedback`. **Bug found and fixed:** CORS was hardcoded to `http://localhost:5173`, but Vite silently falls back to the next free port (5174, 5175, ...) whenever the default is already taken by another running instance — so the dashboard's `fetch` calls were being blocked by the browser itself and misreported to the user as "API unreachable," which looked like a backend problem. It wasn't caught by earlier `curl`-based smoke testing because `curl` doesn't enforce CORS at all — only browsers do. Fixed with `allow_origin_regex=r"http://localhost:\d+"` to match any localhost port rather than one hardcoded value.

### Gmail connector

`gmail_connector.py` — OAuth via `google-auth-oauthlib`'s `InstalledAppFlow` (Desktop-app credentials), token cached to `token.json` so the browser consent flow only runs once. Polls `history.list` every 40s against a `historyId` cursor persisted in the new `SyncState` table, specifically to avoid re-scanning the entire inbox on every cycle. **Bug 1, found and fixed:** `history.list` can fire a `messageAdded` event before the message's subject/snippet are actually indexed on Gmail's side, producing empty content that the LLM would then hallucinate a plausible-sounding score for — a genuine false notification risk. Fixed by skipping messages with empty content and relying on Gmail re-emitting the same event once indexing catches up, so the next poll picks it up correctly. **Bug 2, the serious one, found and fixed:** a `print()` of message content crashed with `UnicodeEncodeError` on Windows' default `cp1252` console encoding whenever a message contained emoji or other non-ASCII characters. That crash happened *after* the offending message's own DB commit but *before* the `historyId` cursor update at the end of the poll cycle — so every subsequent poll restarted from the same stale cursor, reprocessing that same earlier message on every single cycle and never advancing to newer mail. A real test email sent during live testing silently never showed up because of this. Fixed two ways at once: forcing UTF-8 stdout at the CLI entry point (`cli.py`'s `main()`), and wrapping each individual message's processing in its own try/except inside the poll loop, so one bad message can never again block the rest of the batch or prevent the cursor from advancing.

### React dashboard + 👍/👎 feedback UI

`frontend/` — Vite + React + TS. Surfaced/filtered columns are driven directly by the pipeline's own `notified` flag rather than any separate UI-side relevance logic, a focus switcher that waits for the `POST /focus` response before updating displayed state (not optimistic), and 👍/👎 buttons wired to `POST /items/{id}/feedback`. A "hide low-relevance items" toggle was added after real Gmail marketing mail started dominating the Filtered column. **Bug found and fixed:** the first version of that toggle only checked `llm_score <= 1`, which excluded any item with `llm_score === null` — i.e. everything that failed stage 1 and never reached the LLM at all, which turned out to be most of the marketing mail. Fixed to treat `!passed_stage1 || (llm_score !== null && llm_score <= 1)` as low-relevance; verified directly against real DB data before shipping (272 of 278 filtered items were correctly caught by the fixed check). Status: type-checks and builds cleanly end-to-end, but hasn't yet been manually clicked through in a running browser (🟡) — the one item on this list still awaiting that verification pass.

### Feedback-driven threshold tuning

Built as suggestions only — never an automatic write. The audit's re-read of the real data was the key finding: the existing 3 feedback rows (1👍 on a notified item, 2👎 on items that never reached stage 2) carry **zero** actionable signal under a correct mapping, not just "too few to be confident" — a 👎 on an already-filtered item just confirms current behavior, it doesn't argue for tightening anything. `GET /feedback/insights` buckets every `Feedback` row into six state/vote combinations (notified+👎 → raise that source's score threshold; filtered-but-scored+👍 → lower it; never-scored+👍 → lower `embedding_threshold`; every other combination is non-informative and doesn't count), computed live on every call with no `SyncState` key, same philosophy as `GET /health`. Each threshold gets its own independent gate (`feedback_min_votes=10`, a plain `config.py` constant, deliberately not dashboard-tunable) before a direction is surfaced; `SettingsPanel.tsx` shows the suggestion inline under the relevant field, and voting never touches `SyncState` or any threshold value — confirmed live by pushing one threshold past its gate with 11 synthetic votes and checking `GET /settings` stayed unchanged throughout. **Real bug found and fixed along the way:** `create_feedback` was a pure insert with no existing-row check, and `feedback` had no unique constraint on `item_id` — voting twice on the same item without a reload (confirmed live, before the fix) silently created two contradictory rows instead of replacing the vote. Fixed with a dedup-then-`ADD CONSTRAINT` migration (Postgres has no `ADD CONSTRAINT IF NOT EXISTS` — verified, it's a syntax error — and a `DO` block catching `duplicate_object` doesn't work either since a duplicate unique constraint actually raises `DuplicateTable`; checking `pg_constraint` directly is what's actually idempotent) and an upsert endpoint. `ItemOut` gained a `feedback` field so the dashboard shows a prior vote after reload instead of always rendering blank.

### Digest mode

Built per the audit's finalized plan. The digest-worthy band needed no new scoring — reused `App.tsx`'s existing `isLowRelevance` boundary verbatim (`passed_stage1 AND llm_score is not null AND llm_score > 1 AND notified == False`). A daily background thread (`digest.py`) started unconditionally once in `cli.py`'s `cmd_run()` regardless of `--source`, checking every 5 minutes against a configured time (`Settings.digest_time`, default `18:00`, deliberately `.env`-only rather than dashboard-tunable) and a `digest_last_run_date` `SyncState` key — not derived from item data, since a day with zero digest-worthy items would make that derivation wrong in both directions. A one-time backfill (`digest_backfill_done` marker) stamps all pre-existing items as already-digested on first run, so the ~300 items already in the live DB didn't dump into the first toast as one giant notification. **Real bug found and fixed during live testing:** the scheduler originally called `notify.send_notification` synchronously — the exact thing `pipeline.py` already avoids, since `toast()` blocks until dismissed. In a live run this stalled the scheduler thread indefinitely right after its first real firing; `digest_last_run_date` never got recorded and the thread never checked again. Fixed by persisting state before firing the toast and moving the toast call to its own daemon thread, mirroring `pipeline.py`'s existing ordering exactly. **Second inconsistency found and fixed:** the dashboard's Digest section initially ignored `digested_at` entirely, which would have shown every matching item forever, including ones already announced in a past digest — added `digested_at === null` to the frontend filter to mirror the backend job's own query. Live-verified: schema migration and backfill run cleanly and idempotently across repeated restarts, the scheduler doesn't fire before its configured time, fires correctly on its real cadence once the time passes, doesn't re-fire the same day across further restarts, and starts exactly once under `--source gmail`/`slack`/`all`.

### Connector health visibility

Heartbeats reuse the existing `SyncState` key/value table unmodified — no new model, no `init_db()` change. Gmail writes `gmail_last_poll_at` as the literal first statement of every poll cycle (`_poll_once`), before any of its three internal branches run, so a heartbeat fires every cycle regardless of outcome. Slack has no natural polling cadence (Socket Mode is event-driven), so it gets a synthetic heartbeat instead — a dedicated 30s daemon thread, started only after `handler.connect()` succeeds, using plain `threading`/`time.sleep` with no signal handling so it can't reintroduce the earlier SIGINT-on-background-thread bug. `GET /health` reports each connector's last heartbeat, seconds since, and staleness — 3× each connector's own interval (Gmail >120s, Slack >90s); a connector that's never written a heartbeat at all counts as stale/unknown, deliberately not healthy-by-default. The dashboard's status strip folds into the existing single polling `useEffect` in `App.tsx` rather than adding a second `setInterval`. Explicitly out of MVP scope: no escalation/toast-on-stale — a staleness notification risked becoming noisy on its own (firing just because there's been no new mail, not because anything's actually broken), which would undermine the entire point of the project. Verified live against a real HTTP request, not just the both-green happy path: killed the running Gmail listener and confirmed `/health` only flipped to `stale:true` once the 120s threshold had actually been crossed, not before.

### Graceful connector failure handling

Root cause: `slack_app = App(token=...)` was being constructed at module scope, and `App.__init__` eagerly calls `auth_test()` — so this was running at Python *import* time, in the main thread, before any `threading.Thread` had even been created. A dead Slack token therefore crashed the entire process outright, taking Gmail's not-yet-started thread down with it. This wasn't a thread-isolation failure (Python doesn't propagate exceptions between threads by default) — it was a crash that happened *before* threading began at all. Fixed by moving `App(...)` construction and event-handler registration out of module scope and into `start_slack_listener()`, matching the lazy-construction pattern `gmail_connector.py` already used correctly for `get_gmail_service()`. Both are now wrapped in a try/except that records `slack_last_error_at`/`slack_last_error_message` (or the Gmail equivalents) via `SyncState` and returns without re-raising — deliberately no auto-retry, since a dead/invalid credential needs a human to fix the root cause, not a retry loop masking it. The identical fix was applied symmetrically to `gmail_connector.py`, which turned out to have the exact same latent bug, previously unobserved because nothing had triggered it yet. `GET /health` now forces `stale=true` whenever an error is recorded, independent of what the heartbeat timing alone would say. The dashboard gained a third visual state — amber "crashed" (known cause, shown immediately) distinct from red "stale" (gone quiet, unknown why) — the exact distinction this feature exists to surface. Verified live, twice, against real failures rather than simulated ones: once using the actual dead Slack token already present in `.env` (confirmed Gmail ran normally under `--source all` while Slack failed and recorded exactly why, with the process staying up throughout); once by temporarily hiding Gmail's `credentials.json`/`token.json` (confirmed the symmetric result). **Follow-up bug, found during that same verification pass:** a resolved error never cleared itself — fixing credentials and restarting the connector left `/health` still reporting a healthy, working connector as "crashed," since nothing removed the old error record from `SyncState`. Fixed with a new `delete_cursor()` helper that removes the row entirely (rather than writing an empty-string sentinel, since `SyncState.value` is non-nullable) at the exact point a connection is confirmed established — right before Slack's heartbeat thread starts, right before Gmail's poll loop starts. Verified live by hiding then restoring Gmail's credentials a second time and confirming `/health` returned to a genuinely clean `stale:false` state with both error fields `null`, not just a fresh heartbeat sitting next to a stale leftover error.

### In-dashboard tuning controls

Built per the audit's finalized plan, with all three read sites updated: `pipeline.py`'s two score-threshold branches, and `embedding.py:passes_stage1()` for `embedding_threshold` (which now takes `session` as a parameter so it can read `SyncState` directly, rather than pulling from the cached `Settings` singleton). `GET`/`POST /settings` mirror the existing `GET`/`POST /focus` pair; `POST` validates each key against its real bound via pydantic `Field(ge=..., le=...)` — score thresholds `[0, 10]` matching `llm.py`'s hard clamp, embedding threshold `[-1, 1]` matching cosine similarity's true range — so an out-of-range value 422s the whole request before anything is written, no partial updates. `.env`/`Settings` is now purely the bootstrap default, consulted only when `get_cursor` returns `None` for a key; the first `POST /settings` write makes that `SyncState` row win permanently, including across restarts with a stale `.env` still present. `SettingsPanel.tsx` mirrors the focus-switcher's non-optimistic submit-await-update pattern, plus a `try/catch` the focus switcher itself doesn't have — added specifically because silent validation failure on a dashboard (unlike a `.env` edit) could disable notifications with zero feedback to the user. Live-verified with 5 smoke tests against a running server: fresh-install defaults all report `source: "default"`; an out-of-range POST 422s and writes nothing; a single-key override leaves the other two independently unchanged; a threshold change flips the notify decision on the very next message inside the same already-running process, no restart; and an override survives a full process restart despite `.env` still holding the original value. One incidental bug caught and fixed in the throwaway smoke-test script itself (not the feature): reading `item.llm_score`/`item.notified` after `session.close()` hit SQLAlchemy's `expire_on_commit=True` — fixed by capturing both values into locals immediately after `process_item()` returns, before the session closes.

### Self-auditing the AI judge (golden-set regression)

Built as `python -m app.cli audit`, reading `backend/tests/golden_set.json` — the first thing under `backend/tests/` in the project's history, and deliberately not a `pytest` suite, since this is a manually-invoked local command, not a CI step, and adding a whole test framework as a dependency for one fixture file would be overkill. The audit's own investigation found only one of the two motivating regressions actually lived in `llm.score_item()` (the Gmail empty-content hallucination); the Week 1 stage-1 threshold bug was entirely `embedding.py`'s territory. Rather than narrowing scope to just "the LLM" because of the feature's name, the golden set covers both, as two genuinely separate fixture shapes read by one command — 5 `llm` cases asserting an exact `expected_score` via `score_item()`, 3 `embedding` cases asserting an exact `expected_similarity` via `similarity()` directly (not `passes_stage1()`, since that reads the live, dashboard-tunable `embedding_threshold` and would make the assertion depend on whatever the Settings panel currently has it set to, rather than testing the embedding model itself). Every expected value was recorded by actually running the real content through the real functions against the live local Ollama/`sentence-transformers` setup, not guessed — and determinism was verified empirically first: 23 live LLM calls and 6 embedding calls across the audit and the case-authoring pass, zero variance, so exact-value assertions (not ranges) are correct here. One case (`empty_content`) reproduces the actual unfixed Week 2 failure mode on record: `score_item()` still hallucinates a plausible-sounding score (2, with a fabricated justification referencing content that doesn't exist) for empty input — the real fix was only ever applied at the Gmail connector's caller, never inside the function itself, so this case exists specifically to catch that gap if it's ever exercised through a different path. No baseline file — the fixture's own expected values are the only persisted state, updated by a human only in the same commit as an intentional prompt/model change, never automatically. `cmd_audit` prints one `PASS`/`FAIL` line per case and exits non-zero on any failure — purely a scriptability nicety, not real enforcement, since `cmd_run` doesn't check it and nothing currently could. **Live-verified it actually catches a real regression, not just that it runs:** temporarily removed `SYSTEM_PROMPT`'s explicit marketing/bulk-mail rule and reran the audit. The specific case targeted (`marketing_bulk_mail`) still passed — the model judged that content off-topic from context alone even without the explicit rule — but the edit's ripple effect showed up elsewhere: `casual_on_topic_checkin` dropped from 9 to 6 and `urgent_on_topic` rose from 8 to 9, both cases the edit wasn't aimed at. `6/8 passed`, exit code 1. Reverted the prompt (confirmed via `git diff --stat` showing zero diff) and reran: `8/8 passed`, exit code 0, identical to two prior clean runs. Arguably a better proof than the predicted outcome — it caught an unintended side effect of a prompt edit, which is exactly the kind of drift a human re-reading a diff would be likely to miss.

### Attention budget

Built exactly per the audit's plan: a new nullable `queued_at` on `Item`, deliberately not a reuse of Digest's band — a budget-blocked item had cleared the notify threshold and would otherwise silently bucket into tomorrow's Digest toast alongside items that were never going to notify at all, so both the backend digest query and the frontend's `isDigestWorthy` filter now explicitly require `queued_at IS NULL`. The per-day count is a live `COUNT` query (`notified=true AND created_at >= start of today`) rather than a new `SyncState` cursor — fully derivable from existing data, no new counter to keep in sync. `_start_of_today_utc_naive()` in `pipeline.py` computes local midnight and converts it into the same naive-UTC shape `items.created_at` is actually stored in (confirmed live: the column has no timezone, but the value written is UTC wall-clock — a tz-aware cutoff compared directly against it would silently misbehave). Release is a batch job folded into the existing digest scheduler thread (a new `budget_last_release_date` `SyncState` key, same idiom as `digest_last_run_date`) rather than a second thread — items release firing exactly as originally scored, never re-evaluated against a possibly-changed threshold, with one aggregate toast rather than one per item. A score of 9-10 always bypasses the budget entirely, written with an explicit comment flagging this as a starting assumption grounded in only one real 9-10 ever occurring in this project's history, not a settled rule. Default set to 10/day — the real notification history is far too sparse and bursty to derive a "typical day" from (7 Slack notifications fired within one 2.5-hour live-testing window on 2026-08-01, then a single Gmail notification on a different day entirely; no other day has any), so 10 was chosen deliberately above the one observed burst rather than presented as data-derived precision it doesn't have. Live-verified: pushing the live count past a temporarily-lowered budget queued the next threshold-clearing item instead of notifying it (no toast fired); a 9-10 item still notified immediately despite the exhausted budget; a queued item was confirmed absent from Digest via the real predicate; and forcing a date rollover released two queued items as a single batch with one toast, correctly leaving `notified=true`/`queued_at=null` on both.

### Weak-signal escalation across messages

Dashboard flag only, exactly as scoped — never a real notification, never touches the notify/budget path at all, matching the precedent already set by connector-staleness alerts and digest mode's one-toast-per-day design. Two new nullable columns on `Item` (`embedding_vector`, a JSON-encoded list of floats computed only for items that pass stage 1; `cluster_count`, how many similar recent items existed at scoring time) via the same idempotent migration pattern. **The pre-ship validation the audit demanded turned up a real, significant problem, not a rubber stamp.** First run against the actual 2026-08-02 250-item Gmail burst at the planned threshold (0.85): 249 of 250 items falsely flagged, average `cluster_count` ~137. Raising the threshold did not help — computing the full pairwise similarity distribution within the burst showed it's perfectly bimodal (every pair sits at either ~0.12 or ~1.0, nothing in between), so no threshold value between 0.85 and 0.999 changes the result at all; the counts were byte-identical at every threshold tested. The actual cause: the burst is 3 automated senders each resending near-identical content dozens of times, which content-similarity alone cannot distinguish from many different people independently converging on one real topic — both look like near-1.0 similarity in embedding space. Fixed by excluding same-sender pairs from the candidate pool in `count_recent_similar()`, at the same 0.85 threshold (no need to raise it — the problem was never the threshold value). Re-validated against the same burst with the fix applied: max `cluster_count` across all 250 items dropped to exactly 0. Live-verified the fix's logic separately with 4 synthetic messages from 4 *different* senders (simulating genuine multi-person escalation, the case the feature actually exists for) — `cluster_count` climbed 0 → 1 → 2 → 3 as expected, and the dashboard badge (a distinct, separate display threshold from the storage-side similarity threshold) correctly appeared only once count crossed 3. Confirmed both empirically and via code review that `cluster_count` has zero influence on `notified` or any toast — the assignment in `pipeline.py` is the only place the field is referenced anywhere in the codebase.

### On-device personalization via local fine-tuning — deferred

Audited, not built, with an explicit re-trigger condition rather than left as a someday idea. Current real feedback: 3 rows, and per feedback-driven tuning's own established finding, effectively 0 of those carry real signal under a correct reading (a confirming 👍 on a correct notification, two 👎s on items already correctly filtered) — nowhere close to the low-hundreds-to-low-thousands a LoRA adapter would realistically need to generalize rather than memorize noise on a task with genuine semantic variance. Noted for whenever this is revisited rather than solved now: this machine has no discrete GPU, so LoRA training would still mean full forward/backward passes through the frozen 3B base network per step without one, likely many hours per run; the toolchain (`peft`/`transformers`, HuggingFace-format checkpoints) is entirely separate from Ollama's GGUF-based serving, and a trained adapter would need conversion via `llama.cpp` tooling before Ollama's `Modelfile` `ADAPTER` directive could load it — a real gap worth knowing about before starting, not discovering partway through. Concrete re-trigger, mirroring `feedback_min_votes`'s own precedent rather than "someday": revisit once real feedback reaches at least 200 rows with genuine coverage across both 👍/👎 and both sources, using the informative-vote logic feedback-driven tuning already built to distinguish real signal from noise at that point, not just a raw row count crossing 200.

### Per-sender adaptive trust — deferred

Audited, not built — a "no current justification to build" deferral, not a "don't know how to build it" one. The audit checked real per-sender data live against the actual 320-item DB and found the feature has nothing to fix today: `ProPeers <no-reply@propeers.in>` (166 items) and `Slack <no-reply@email.slackhq.com>` (22 items) both already average `llm_score` 0.0 with 0 notifications — floored by `SYSTEM_PROMPT`'s existing hardcoded marketing/bulk-mail rule, so a downward trust delta would have nothing left to adjust. `Nykaa <noreply@nykaa.com>` (83 items) never passes stage 1 at all, so `llm_score` is never computed and the feature's insertion point (a post-`score_item()` adjustment) never runs for that sender regardless of design. The one sender with genuine score variance, the Slack user `U0BLTLJJQ1M` (23 items, avg `llm_score` 4.67, 7 notified), is a real human collaborator, not noise — and its single feedback row is a 👍 on a notification, i.e. evidence the current unadjusted handling is already correct, making it the wrong sender to justify a suppression feature against. The two loudest "noisy" senders are already solved by content-based scoring; the one sender with headroom is the one a downward prior would put at risk.

The full design was still worked out, since the audit's job was to answer whether it's buildable, not just whether it's needed yet, and it's sound: insertion point is a new nullable `adjusted_score` field computed in `pipeline.py` right after `llm.score_item()` returns, deliberately not a mutation of `llm_score` itself (same "adjunct field, not overwrite" pattern as `cluster_count`/`queued_at`) — this keeps `GET /feedback/insights` reading the unadjusted LLM judgment, so a sender's trust prior can never get folded back into feedback-driven tuning's own signal. Senders that never clear stage 1 (like Nykaa) are out of scope by construction, not a gap to close. A minimum-history gate (proposed 15 scored items, mirroring `feedback_min_votes`'s precedent) would clear for only 3 of the 22 real senders today. Feedback votes are excluded from v1 — only 3 rows exist total, the same thin-data wall feedback-driven tuning's own audit already hit. Blend math: a bounded additive delta (`clamp((sender_avg − global_avg) × dampening, -2, +2)`), forced to exactly 0 below the minimum-history gate so a brand-new sender's first message is never suppressed by a prior that doesn't exist yet. Critically, the attention budget's existing 9-10 always-notify bypass must check the raw `llm_score`, never `adjusted_score` — a downward sender prior must never be able to strip an otherwise-urgent message of its bypass eligibility. The golden set (`backend/tests/golden_set.json`) is entirely unaffected, since it calls `score_item()` directly and the adjustment would live outside that function, in `pipeline.py`.

**Concrete re-trigger, an event rather than a volume/time threshold:** revisit when a specific sender clears the 15-scored-item minimum with a scored average above that source's notify threshold, *and* has real feedback indicating the current per-message scoring is actually getting that sender wrong — not just a theoretical case, a sender the live data can point to.

### Calendar integration / auto-focus detection

New `backend/app/connectors/calendar_connector.py`, deliberately independent from Gmail's connector despite sharing the same OAuth client: its own scope (`calendar.readonly`), its own cached token (`backend/calendar_token.json`, gitignored — added to `.gitignore` mid-build after almost getting committed as an untracked secret), its own error/heartbeat keys, so a Calendar-specific problem can never take down Gmail's already-working credentials or vice versa. No `historyId`-style cursor like Gmail — calendar state is "what's true right now," not an append-only log, so each poll (every 180s) just recomputes fresh: `events.list(timeMin=now, timeMax=now+15min, singleEvents=true)`, filtered to qualifying events (2+ attendees, self `responseStatus == "accepted"`, `transparency != "transparent"`, timed not all-day), picking the first in `startTime` order (tiebreak on event ID — an arbitrary but deterministic placeholder, not yet informed by any real double-booking case).

`FocusState` gained a nullable `source` column (`"manual" | "calendar"`, NULL on every pre-existing row, treated as manual everywhere it's read). Auto-focus reuses the existing "most recent row wins" read logic rather than adding new precedence code: a meeting start writes a new `source="calendar"` row with the event's title; a manual edit at any time simply becomes the newest row and wins for free; a meeting end only reverts to the last manual-source text if the *current* latest row is still `source="calendar"` — if a manual edit happened during the meeting, it's already latest and end-of-meeting reversion correctly leaves it alone. Meeting suppression raises the effective notify threshold to 9 (via a cached `calendar_busy_until` `SyncState` cursor `pipeline.py` reads locally — never a live Calendar API call per incoming message) without ever touching `item.llm_score` itself, and the existing 9-10 attention-budget bypass keeps reading the raw score, so a genuinely urgent message during a meeting notifies exactly as it would outside one. A suppressed sub-9 item that still passed stage 1 needs no new state — it falls through to the existing Digest section on its own.

**Live-verified against two real calendar events** (not just synthetic data): a genuine start transition fired correctly for both meetings (`FocusState` row with `source="calendar"` and the real event title, `calendar_busy_until` set to the real end time); a back-to-back transition between the two meetings correctly produced just a new start with no spurious revert in between (an edge case the design anticipated but hadn't been proven); and the end-of-meeting reversion fired correctly once the connector's connectivity recovered from an extended real network outage (the live process logged dozens of `WinError 10054`/DNS-failure poll errors across several hours — consistent with the machine sleeping — each caught by the existing per-connector try/except without crashing or affecting Gmail/Slack, and the very next successful poll correctly detected the meeting had ended and reverted focus, ~18 hours later than the meeting's actual end time but logically correct given the process had no way to poll while offline). The meeting-suppression threshold raise and the manual-override precedence rule were verified by directly driving the same production code paths (`process_item()`, the real `_poll_once()`, the real `POST /focus` endpoint) with a manually-set `calendar_busy_until`/fake event ID rather than waiting on a third live meeting — the always-running background poller independently logged the same "manual override already in effect, no revert" outcome during this window, confirming the manual test matched real production behavior rather than just a script's own logic. One real message scoring 8 was correctly suppressed (`notified=False`); one scoring 9 still notified despite the simulated meeting, confirming the budget-bypass invariant holds under meeting suppression too. **Found and fixed one real bug along the way:** `POST /focus` returned a 500 (`ResponseValidationError`, missing `calendar_busy`) because only `GET /focus` was attaching the computed `calendar_busy` attribute before the schema required it — the underlying write always succeeded, only the response serialization failed; `update_focus` now attaches it too.

**Known non-goal, flagged honestly rather than silently observed:** while testing meeting suppression, the same two message contents scored differently between an isolated `score_item()` call and a `process_item()` call moments later (an 8 and a 9 swapped) — a real deviation from this project's earlier "zero variance across 23 calls" determinism finding (see the self-auditing writeup above). Not investigated further here since it's outside this feature's scope, but worth knowing the golden-set audit's exact-value assertions rest on an assumption that may be less airtight than originally measured.

### Flow-state-aware dynamic strictness — validation phase

`backend/app/services/flow_state.py`: idle-time and foreground-process-name detection via plain `ctypes` calls into `user32.dll`/`kernel32.dll` (`GetLastInputInfo` for idle time, `GetForegroundWindow` + `GetWindowThreadProcessId` + `QueryFullProcessImageNameW` for the process name) — no new dependency, as the idea's own writeup proposed. Confirmed working live on the first try: correctly identified `Code.exe` as the foreground process with near-zero idle time while this session was running.

Per the plan's mandatory pre-ship validation gate (the same one weak-signal escalation's real false-positive finding established), this is deliberately **not yet wired into any notify/threshold decision**. A background thread (started unconditionally in `cli.py`, same pattern as digest/calendar) samples every 60s and appends `(timestamp, idle_seconds, process_name)` to a gitignored local file (`backend/flow_state_samples.log`) during real daily use — process name only, never window titles, per the idea's own privacy constraint. Once a few real days of samples exist, the next step is hand-checking whether derived "flow" periods actually line up with genuine focused stretches before picking calibration constants or writing any suppression logic.

### GitHub-aware auto-reply with actionable notifications — Tier A built, Tier B deferred

**Tier A scope and what changed from the original idea:** built exactly to the split the win11toast feasibility investigation established — reliably catching a click made while the toast is still on-screen, not a click from Action Center after it times out (see that investigation's findings above the idea writeup). Tier B (a real `INotificationActivationCallback` COM server for delayed clicks) is explicitly deferred, not stubbed, same pattern as fine-tuning and per-sender trust: re-trigger signal is `reply_posted_at` staying mostly null in practice once Tier A is live against real traffic.

**Permanent app identity (`backend/app/services/app_identity.py`, `backend/scripts/create_app_shortcut.ps1`):** every actionable toast needs a Start Menu shortcut carrying a matching AppUserModelID (AUMID), same requirement the feasibility investigation found. Building the permanent version surfaced two new real bugs beyond what that investigation already found:
1. The first shortcut-creation script hand-rolled an `IShellLinkW` → `IPropertyStore` QueryInterface cast via `Add-Type` C# COM interop. It reliably threw `ArgumentException: Value does not fall within the expected range` and silently never wrote the shortcut file at all, while still printing a success message (the exception happened before the script's own error handling could catch it). Fixed by splitting the operation in two: create the plain shortcut via the well-tested `WScript.Shell` COM object, then apply the AppUserModelID property afterwards via `SHGetPropertyStoreFromParsingName` — avoids the fragile cast entirely.
2. Even after that fix, the specific AUMID `SignalFilter.App` never rendered buttons, while an identical setup under a brand-new never-before-used AUMID worked immediately. Windows appears to cache a broken/negative registration per-AUMID from the first script's failed attempts — confirmed by testing three ways (fresh AUMID + string buttons, fresh AUMID + real click, and finally the permanent AUMID `SignalFilter.Notifier` + the exact production dict-form buttons), all working and all producing a real captured click (`arguments: 'reply_yes'` matching the clicked button exactly). Rather than fight a Windows-side cache with unknown invalidation rules, the permanent AUMID was simply renamed to one never touched by the broken attempts — documented in `app_identity.py` so this doesn't get re-debugged from scratch later.

**Repo indexing (`backend/app/services/repo_index.py`):** an in-memory index rebuilt every 10 minutes from `git log` (`sha`, `subject`, `body`, embedding via the existing `embedding.get_embedding()` — no new model), matching this repo's small size rather than a persistent table, per the plan's "prove it works on real data first" preference. Match threshold calibrated against 4 real question/commit pairs against this repo's actual history: genuine matches scored 0.577–0.618, an unrelated question scored 0.202, and one paraphrase-heavy question ("did the weak signal clustering false-positive bug get fixed?") missed its true match entirely, ranking a wrong commit at 0.360 instead — a real, expected limitation of pure cosine similarity, not a bug. `MATCH_SIMILARITY_THRESHOLD = 0.55` sits just under the lowest real match and comfortably above that false-lead score. Small sample, not a settled constant — same caveat weak-signal escalation's threshold carries.

**Reply drafting (`llm.py`'s `draft_reply_from_commit`):** a distinct LLM call from `score_item()`'s, with its own system prompt. The first version of that prompt leaned heavily on warning language ("a wrong reply is worse than no reply — default to NOT confident") and, live-tested, turned out to **always** return `confident=false` — including for a maximally obvious synthetic case (a commit literally saying "dark mode is now available and working" against the question "is dark mode implemented yet?"). This was a real prompt-design bug, not appropriate conservatism: the small 3B model was pattern-matching the alarmed tone rather than evaluating the actual evidence. Fixed by rewriting the prompt with concrete positive/negative examples (mirroring `score_item`'s own working style) instead of warnings — re-tested against 5 cases (2 expected-confident, 2 expected-not-confident, 1 real borderline case) and got 4/5 correct, with the one miss being a defensible conservative call on a genuinely ambiguous pair (redacting tokens vs. "resolving the issue").

**Schema:** `Item` gained `drafted_reply` (text), `reply_posted_at` (nullable timestamptz — the idempotency guard against a double-click, and the future signal for whether Tier A's immediate-click window is wide enough in practice), and `channel` (Slack channel ID). The last one was a real gap found while building this: `thread_id` already falls back to the channel ID for non-threaded messages, so it can't be trusted as "the channel" for posting a reply. Rather than touch that existing (working, relied-on) fallback behavior, added a clean `channel` column and used the message's own `source_timestamp` as the reply's `thread_ts` anchor — valid for both already-threaded and top-level messages, since Slack accepts any message timestamp as a thread root.

**Delivery:** `notify.py` sends a plain toast as before, or — when `drafted_reply`, `item_id`, and `channel` are all present — an actionable one with `Yes, post it` / `No` buttons (`activationType: "foreground"`, custom `arguments`, the format confirmed working above). The click handler is idempotent (`reply_posted_at is not None` short-circuits a double-click), always records the click as feedback via the same `Feedback` upsert the dashboard's 👍/👎 buttons use (`app/services/feedback.py`, extracted from what was previously inline logic in `main.py`'s `create_feedback` endpoint so both call sites share it), and only actually posts to Slack on Yes — a failed post (e.g. missing scope) leaves `reply_posted_at` null rather than silently pretending to have succeeded.

**End-to-end live verification:** drafting, matching, DB persistence, click handling, feedback capture, and idempotency were all tested together against a real synthetic item built from this repo's actual commit history (the real POST /focus 500-error fix), inserted and cleaned up without touching the live running process's actual focus state or real Slack API — deliberately avoided live-firing a real Slack post since the `chat:write` scope isn't added yet (TODO.md #5). Actionable toast delivery itself was separately live-verified with real clicks captured under the permanent AUMID.

## The idea

You're not overwhelmed because you get too many notifications — you're overwhelmed because most of them don't matter right now. Signal Filter learns what you're currently focused on (a short text you set, updated throughout the day) and only interrupts you for things actually relevant to that, muting the rest instead of silently dropping it.

**Why it's hard:** priorities shift hour to hour, and "urgent" is relative to your current focus, not urgent in general. The system needs to understand meaning (not keyword/sender rules) and do it fast enough to triage in real time across Slack and Gmail.

## Tech stack & key decisions

| Area | Choice | Why |
|---|---|---|
| Storage | PostgreSQL (local) | Chosen partly to get Postgres practice; SQLAlchemy models make it easy to swap later if ever needed |
| Stage-1 embeddings | `sentence-transformers` — `all-MiniLM-L6-v2` | Local, free, fast enough on CPU for cheap similarity scoring |
| Stage-2 LLM | Local via **Ollama** — `qwen2.5:3b-instruct` | Free (no API cost); smaller + better instruction-following/structured output than `phi3:mini`, important given CPU-only inference (16GB RAM, Intel Iris Xe iGPU, no discrete GPU) |
| Repo structure | Monorepo (`/backend`, `/frontend` later) | Simplest for a solo MVP, no separate deploy targets yet |
| Notification delivery | Native Windows toast notifications | `win11toast` or `winsdk` — not `win10toast`, which is unmaintained/flaky on modern Windows |
| Frontend | Deferred — CLI first | Backend/pipeline needs to work before a dashboard is useful |
| Cost constraint | Everything must be free | No paid APIs or cloud resources anywhere in the stack |

## Architecture

### Data layer

- **Slack**: Socket Mode — receives events without needing a public URL (no ngrok, no public hosting for MVP)
- **Gmail**: polling via `history.list` every 30–60s — no Pub/Sub push setup needed for MVP
- Normalize everything into a unified `Item` schema: `{source, sender, content, timestamp, thread_id}`
- Postgres via SQLAlchemy

### Intelligence layer — two-stage ranking pipeline

Every incoming message runs through two stages before a notification decision is made:

| Stage | Name | What happens | Tech | Threshold / behavior | Output |
|---|---|---|---|---|---|
| 1 | Embedding filter | Embed the incoming item's text and the user's current focus string, then compute cosine similarity between the two vectors. This is the cheap, fast pass that runs on *every* message. | `sentence-transformers` — `all-MiniLM-L6-v2`, local, CPU | Start **permissive/low** — a missed urgent message is worse than a few extra LLM calls downstream. Raise it later once feedback data justifies tightening it. | A similarity score (0–1). Items below threshold are filtered straight to the low-priority digest, skipping stage 2 entirely — this is what keeps the pipeline fast and free. |
| 2 | LLM judgment | Only items that clear the stage-1 threshold get sent here. The LLM reads the message plus the user's focus string and reasons about semantic relevance, urgency, and context (e.g. "is this actually blocking something," not just "does it mention similar words"). | Local `qwen2.5:3b-instruct` via Ollama, CPU inference | No threshold to tune yet — every item that reaches this stage gets scored. Prompt should ask for a structured output (e.g. JSON with a 0–10 interrupt score + one-line reason). | A final interrupt score + short justification. Above a cutoff → native Windows notification fires. Below it → item stays in the CLI/dashboard stream but doesn't interrupt. |

**Feedback loop** (runs alongside both stages, not a stage itself): log 👍/👎 on every triage decision to Postgres **from day one** — embedding score, LLM score, and user feedback together — even before anything consumes it. Much easier to capture this now than to retrofit it once real usage data exists.

### Delivery

- Native Windows notification only for the top-ranked/high-interrupt items
- Everything else stays visible in CLI output (later: dashboard digest) — never silently discarded

## Week 3+ (Tier A done, Tier B deferred): GitHub-aware auto-reply with actionable notifications

**Status: Tier A built and live-verified; Tier B explicitly deferred.** See the Technical Summary entry above for what was actually built (app identity, repo indexing, reply drafting, delivery, feedback capture) and the two real bugs found and fixed along the way (a broken shortcut-creation script, and a reply-drafting prompt that always said "not confident"). Tier B (a real Windows `INotificationActivationCallback` COM server, needed for a click made after the toast's own display window) is recorded here rather than silently absorbed into Tier A's build, per the explicit instruction that drove this split — its own re-trigger condition is `reply_posted_at` staying mostly null in practice once Tier A sees real traffic.

**The idea:** connect a GitHub repo to Signal Filter. When a Slack question comes in that's already answered by something already committed (e.g. "did you fix the pipeline bug?" and there's a commit that did exactly that), the system drafts a reply from that commit instead of just notifying you to go answer it yourself. If nothing in the repo answers the question, it falls back to today's normal notify-only behavior.

**How the decision would extend the existing two-stage pipeline (a third branch, not a replacement):**

1. Stage 1 (embedding filter) and stage 2 (LLM relevance/urgency score) run exactly as they do today.
2. For items that clear the notify threshold, an additional check runs: *does this question already have a confident answer in recent commit history?* This needs its own retrieval step (embed commit messages/diffs/README — a small RAG index over the repo) and a separate LLM call whose job is specifically "does commit X answer question Y, and if so draft a short reply" — a QA task, distinct from the relevance-scoring task stage 2 already does. This step needs a **high confidence bar**: a wrong or hallucinated answer posted into Slack under your name is a much worse failure than no reply at all.
3. Outcome branches:
   - No confident answer found in the repo → normal notify, exactly like today.
   - Confident answer found → still notify, but the notification itself carries the drafted reply, not just the original message.

**Delivery mechanic — actionable Windows notification:**

- The native toast includes the drafted reply text plus two buttons: **Yes** (post it) / **No** (stale or wrong, don't post).
- `win11toast` supports action buttons via an `on_click` callback, so this is feasible with the notification library already in use — no new dependency needed.
- Because the click might happen well after the toast fires, the drafted reply and its target channel/thread ID need to be **persisted** (in the `items` row, not just held in memory) so whichever button gets clicked later still has everything it needs to act.
- **Yes** → the bot posts the drafted reply into the original Slack thread (needs the `chat:write` scope added — the bot is currently read-only).
- **No** → nothing gets posted; you go reply manually in Slack yourself, same as today.

**Why this doubles as the feedback loop:** clicking Yes/No on a drafted reply is functionally the same signal as the 👍/👎 feedback already planned for the dashboard (was the system's judgment correct?), just captured at the moment of interruption instead of requiring a later visit to a UI. That data can feed the same threshold-tuning work already planned for Week 3+.

**Open questions, now resolved for Tier A (see Technical Summary above):**

- ~~How to index the repo for retrieval~~ — resolved: last 200 commits' subject+body, no diffs, rebuilt every 10 minutes.
- ~~Where to set the confidence threshold~~ — resolved for now: 0.55 cosine-similarity match gate plus a separate LLM confidence check, calibrated against 4 real question/commit pairs. Small sample, not settled — same caveat every other calibrated constant in this project carries.
- ~~Needs the Slack bot's scopes expanded to include `chat:write`~~ — code path is built; the actual scope addition is TODO.md #5, a real user action still outstanding.

**Still genuinely open:**

- Whether this only applies to your own repos, or also team repos you don't solely own (a permissions/trust question, not just a technical one) — Tier A is hardcoded to this one repo, so this hasn't needed an answer yet.

## Week 3+ (done): Connector health visibility

**The idea:** make it obvious, at a glance, whether each connector (Slack, Gmail) is actually making progress — not just "the process is running," but "it successfully checked for new messages recently." This was a direct response to a real bug found during Week 2 live testing: the Gmail poller got stuck reprocessing the same message on every cycle for over eight minutes, and nothing in the running output made that obvious — it took manually comparing database timestamps and process state to diagnose. A silent failure like that could easily go unnoticed for hours in normal use, quietly missing every real email in the meantime.

**What was built (MVP scope):**

- Each connector writes a heartbeat timestamp on every cycle — Gmail updates `gmail_last_poll_at` at the start of every poll (every 40s), regardless of whether anything new showed up; Slack updates `slack_last_heartbeat_at` every 30s from a dedicated background thread started once its socket connection is established.
- Heartbeats reuse the existing `SyncState` key/value table (same pattern as the Gmail history cursor) — no new schema needed.
- `GET /health` (`backend/app/main.py`) returns each connector's last heartbeat, seconds since, and whether it's stale — staleness threshold is 3× each connector's own heartbeat interval (120s for Gmail, 90s for Slack).
- Dashboard status strip (`frontend/src/ConnectorStatus.tsx`) — a colored dot + "checked Ns ago" per connector, polled alongside items/focus.
- Verified live by killing the Gmail listener and watching `/health` flip from fresh to stale as the threshold passed, then confirming a restart brought it back to healthy.

**Explicitly not built (deliberately out of MVP scope):** no escalation/toast-on-stale. A heartbeat-staleness notification risks becoming noisy on its own (e.g. firing just because there's been no new mail, not because anything's actually broken), which would undermine the whole point of the project. Revisit only if silent staleness turns out to be a real recurring problem in practice.

## Week 3+ (done): Graceful connector failure handling

**The idea:** a connector should never be able to take the whole process — and the *other* connector — down with it. This was triggered by a real crash found while building health visibility above: the Slack bot token had gone dead (`account_inactive`), and `slack_bolt.App(...)` calls `auth_test()` eagerly inside its constructor. That constructor was running at *module import time*, in the main thread, before any connector thread was even started — so the exception killed the entire process, taking a perfectly healthy Gmail connector down with it. It wasn't a thread-safety bug (Python doesn't propagate exceptions between threads by default); it was a crash that happened *before* threading began.

**What was built:**

- Both `App(...)` construction (Slack) and `get_gmail_service()` (Gmail) already happen lazily inside each connector's `start_*_listener()` function rather than at module scope — Gmail already worked this way; Slack's `App(...)` and event-handler registration were moved out of module scope to match.
- Each `start_*_listener()` wraps its connection step in try/except. On failure: print the error, record it (`{name}_last_error_at` / `{name}_last_error_message` via `SyncState`), and return — the thread ends cleanly, the process and the other connector are unaffected. **No auto-retry** — an invalid token or missing credentials needs a human to fix the root cause, not a retry loop masking it.
- `GET /health` treats a recorded error as an automatic override: `stale` is forced `true` whenever `last_error_at` is present, regardless of what heartbeat timing alone would say. The dashboard status dot distinguishes "crashed" (known cause, shown immediately) from "stale" (gone quiet, unknown why) — `ConnectorStatus.tsx`'s `dotClass()`.
- **Follow-up fix, same feature:** the first version left a resolved error stuck forever — fixing credentials and restarting cleared nothing, since no code path removed the old error record, so a genuinely healthy connector kept reporting as crashed. Fixed by clearing `{name}_last_error_at`/`_message` at the exact point a connector's connection is confirmed established (right before Slack's heartbeat thread starts; right before Gmail's poll loop starts) — via a new `delete_cursor()` helper in `sync_state.py` rather than an empty-string sentinel, since `SyncState.value` is non-nullable and a deleted row is what `get_cursor()` already treats as "no error."
- Verified live, twice over: (a) with the actual dead Slack token in `.env`, confirmed Gmail ran normally under `--source all` while Slack failed and recorded why, process alive throughout; (b) temporarily hid `credentials.json`/`token.json`, confirmed Gmail failed the same way and recorded the error, then restored the files and restarted, confirming `/health` returned to a clean `stale: false` state with both error fields `null` — not just a fresh heartbeat sitting next to a stale leftover error.

**Explicitly not built:** any retry logic, any acknowledgment flow, any history/log of past errors, any UI for viewing past crashes. A crash is either currently true (shown) or resolved (cleared) — there's no in-between state or audit trail. If a persistent incident log is ever wanted, that's a different feature, not a variant of this one.

**Still outstanding (unrelated to this fix, pre-existing):** the real Slack bot token in `.env` is genuinely dead and needs regenerating from [api.slack.com/apps](https://api.slack.com/apps) — this feature makes that failure *survivable*, not *resolved*.

## Week 3+ (done): In-dashboard tuning controls

**The idea:** stop requiring a code edit + process restart every time a threshold needs adjusting. Every tuning conversation during Week 2 (embedding threshold, per-source notify threshold) ended the same way: edit `.env` or `config.py`, kill the running listener, restart it, wait for models to reload — a slow loop that also meant losing whatever the connector was mid-processing. Exposing the tunable values through the API and dashboard turns that into something adjustable live, no restart required.

**Status: built and live-verified.** See the Technical Summary entry above for what was actually implemented and tested; the plan below is kept as-written since the build matched it exactly.

**Exact read sites (three, across two files, not one):** `pipeline.py:42/44` reads `interrupt_score_threshold`/`gmail_interrupt_score_threshold` directly; `embedding_threshold` is read one layer down, inside `embedding.py:22`'s `passes_stage1()`, not in `pipeline.py` itself. Both need editing. No other file touches these three keys — `slack_connector.py`, `db.py`, and `llm.py` all import the same `settings` singleton but only for unrelated fields.

**How it will work:**

- Reuse `SyncState` (same pattern as heartbeats/error state) with keys `embedding_threshold`, `interrupt_score_threshold`, `gmail_interrupt_score_threshold` — matching the existing `.env` variable names exactly. No schema change needed; `get_cursor`/`set_cursor` already store everything as strings, cast at the call site (same as the Gmail history cursor and heartbeat timestamps already do).
- `GET /settings` / `POST /settings`, mirroring the existing `GET`/`POST /focus` pair in `main.py`.
- Dashboard: a small panel, number inputs, matching the focus-switcher's actual pattern — not optimistic, waits for the POST response before updating displayed state. One gap worth deciding at build time, not silently inherited: `handleFocusSubmit` has no `try/catch`, so a failed `POST /focus` today becomes an unhandled promise rejection with nothing shown to the user. Replicating that for settings would make the validation below (invisible) — recommend adding a `try/catch` here even though it means not matching the focus pattern 1:1.

**Validation — resolved, not left open:** reject out-of-range values with a 422 rather than accepting anything, specifically because this is a dashboard, not a config file — a fast, unreviewed edit here (unlike a `.env` edit + restart) can silently produce "notifications never fire again" with no feedback. The ranges aren't invented: `llm.py:65` already hard-clamps the LLM's score to `0–10`, so `interrupt_score_threshold`/`gmail_interrupt_score_threshold` reject outside `[0, 10]`; `embedding_threshold` (cosine similarity) rejects outside its true mathematical range, `[-1, 1]`.

**`.env` relationship — resolved, and corrected from the original idea:** the original write-up assumed this should mirror how focus text works. It doesn't apply — `focus.py` has **no** `.env` seeding at all (verified: no `FOCUS_TEXT` setting exists; `get_current_focus()` returns `None` with no fallback until a human runs `focus` for the first time). Thresholds need to behave differently, since — unlike focus text — they need *some* working value from the very first message, before the dashboard's ever opened. Precise rule: `.env`/`Settings` is the bootstrap default, consulted only when no `SyncState` row exists for that key. The first `POST /settings` write for a key makes that row permanent — it wins on every read from then on, including after a restart with a stale `.env` value still present; `.env` only matters again if the row is deleted manually.

**Fallback on `GET /settings` with no override yet — resolved:** always return the current effective value (DB override, else the `.env` default) — never `null`/"unset". Unlike heartbeats, a never-overridden threshold isn't stale or unknown, it's a real value with no time-decay risk, so there's no reason to make the input look empty or broken on a fresh install.

## Week 3+ (done): Digest mode

**The idea:** right now every item is either interrupt-worthy (notifies immediately) or filtered (sits quietly, only visible if you happen to open the dashboard). That binary throws away a real middle ground — a message that's genuinely relevant but not urgent *right now* might still be worth knowing about by the end of the day, without deserving a real-time interrupt. A digest surfaces that middle band on its own schedule instead of losing it in the Filtered list forever.

**Status: built and live-verified.** See the Technical Summary entry above for what was actually implemented, the two bugs found during testing, and how it was tested; the plan below is kept as-written since the build matched it exactly.

**Score band:** no new scoring logic needed. `passed_stage1 AND llm_score is not null AND llm_score > 1 AND notified == False` — the `> 1` cutoff reused verbatim from `App.tsx`'s existing `isLowRelevance` check, so digest-worthy is precisely "what's in Filtered today, minus what's already hidden as low-relevance." Not per-source; the existing low-relevance cutoff isn't per-source either.

**Cadence and delivery:** one low-priority summary toast per day ("4 things worth a look from today"), not per-item — a stream of digest interrupts would recreate the exact noise problem this project exists to prevent, the same reasoning that already ruled out a staleness alert for connector health. A daily background thread in the existing listener process, same pattern as Slack's synthetic heartbeat thread — no Task Scheduler/cron dependency needed since the process runs continuously. Clicking the toast does nothing special, it's just a nudge to open the dashboard, which gets its own dedicated "Digest" section showing the same band.

**Avoiding repeats:** a nullable `digested_at` timestamp on `Item` (the first new column since Week 1) so a digest only ever pulls items created since the last one ran, and marks them after.

Give yourself a daily interrupt budget — once it's spent, even a message that would normally clear the threshold gets queued instead of firing immediately.

## Week 3+ idea: On-device personalization via local fine-tuning — audited, deferred

**Status: explicitly deferred, not built, not stubbed.** See the Technical Summary entry above for the full reasoning and the concrete re-trigger gate (200+ genuinely informative feedback rows). Recorded here so the decision isn't lost as "someday" — it's a specific, checkable condition, mirroring how `feedback_min_votes` gates feedback-driven tuning's own suggestions.

**The idea:** the feedback-driven tuning already planned for Week 3+ adjusts a single threshold number from 👍/👎 data. This goes further — periodically fine-tune (e.g. LoRA-adapt) the local `qwen2.5:3b-instruct` model itself on your accumulated feedback, so the model's actual judgment adapts to your specific taste over time rather than just a static prompt plus a global cutoff. Consumer "personalization" almost always means preference toggles; on-device model adaptation from real usage is rare even in commercial products, and fits the project's zero-cost/fully-local ethos exactly.

**How it would work:**

- Periodically (e.g. weekly, run manually or via a scheduled task) export `(focus_text, content, llm_score, thumbs_up)` rows from the `items`/`feedback` tables as a small training set.
- Run a LoRA fine-tune pass on `qwen2.5:3b-instruct` using that set — Ollama doesn't do this natively, so this would likely mean a separate local fine-tuning toolchain (e.g. `unsloth` or plain `peft`/`transformers`) producing an adapter, then serving the adapted model through Ollama (via a custom Modelfile layering the LoRA weights) instead of the stock model.
- Needs a clear rollback path — keep the previous adapter/model available and compare scoring behavior on the golden-set regression (see the self-auditing idea below) before fully switching over, since a bad fine-tune could silently make judgment worse, not better.

**Open questions to resolve before building this:**

- Is there realistically enough feedback volume from single-user usage to make fine-tuning meaningful, or does it need weeks/months of data first?
- CPU-only fine-tuning (no discrete GPU) may be slow even for a 3B model with LoRA — needs a feasibility check before committing to this over just the simpler threshold-tuning approach.
- How to validate a new fine-tune didn't regress before trusting it live — ties directly into the self-auditing/golden-set idea below.

## Week 3+ (validation phase): Flow-state-aware dynamic strictness

**Status: detection built and confirmed working live; suppression logic deliberately not written yet.** See the Technical Summary entry above — a background thread is logging real (idle, process) samples during real daily use to a gitignored local file. Next step is hand-checking those samples against genuinely focused stretches before picking any calibration constants, per this project's established pre-ship validation gate (the same one that caught weak-signal escalation's real false-positive problem before it shipped).

**The idea:** the calendar integration already planned suppresses interrupts based on explicit calendar state ("in a meeting"). This goes further using purely local, passive signals: read idle time and active-window activity (no cloud, no calendar needed) to infer whether you're in deep, uninterrupted flow versus already context-switching a lot, and dynamically raise or lower the interrupt threshold based on that inferred state — not just a binary busy/free from a calendar, but real behavioral signal about how deep you currently are.

**How it would work:**

- A lightweight local background check (built via plain `ctypes` — `GetLastInputInfo` for idle time, `GetForegroundWindow`/`GetWindowThreadProcessId`/`QueryFullProcessImageNameW` for the active process — no `pywin32`/`pygetwindow` dependency needed after all) samples periodically: how long has the active window been the same, how recently was there input activity.
- Derive a rough "flow score" — long uninterrupted stretch in one app = likely deep focus = raise the interrupt threshold temporarily; frequent window-switching = already fragmented attention = threshold can relax back to normal, since an extra interrupt costs less right now.
- Feed this as a temporary multiplier/offset on top of whatever the per-source threshold already is (from the in-dashboard tuning controls idea), not a replacement for it.

**Resolved:** tracks **process name**, not window title — avoids the privacy concern below entirely rather than needing to scrub titles after the fact.

**Still open, needs real sample data to answer (data gathering now in progress):**

- How to calibrate "deep flow" vs. just idle/away from keyboard — long inactivity isn't the same as long focus, and the signal needs to distinguish them (e.g. idle time near zero + same window for a long stretch = flow; idle time high = probably not at the desk at all).
- Does this apply globally or only during hours you'd otherwise expect to be working?

## Week 3+ (done): Self-auditing the AI judge

Keep a small fixed "golden set" of representative messages with known-expected scores, and automatically re-run it after any change to the prompt, thresholds, or model, so drift gets caught before it's trusted.

**Status: built and live-verified to catch a real regression.** See the Technical Summary entry above for what was actually implemented (including the scope correction — this covers both `llm.score_item()` and `embedding.similarity()`, not just the LLM, since only one of the two motivating regressions was actually LLM territory), the exact fixture format, and the live test that proved it catches drift, not just that it runs.

## Week 3+ idea: Per-sender adaptive trust — audited, deferred

**Status: explicitly deferred, not built, not stubbed.** See the Technical Summary entry above for the full reasoning and the concrete re-trigger condition (a specific sender clearing a 15-scored-item minimum with a scored average above its notify threshold, plus real feedback showing the current scoring is actually wrong for that sender — not a row count crossing a number over time). Recorded here so the decision isn't lost as "someday" — real data was checked live and it's a specific, checkable condition, same pattern as the fine-tuning deferral above.

**The idea:** right now relevance is judged purely from message content against the focus text — the sender's identity plays no role beyond being included in the LLM prompt as context. But real-world triage isn't purely content-based: some senders are reliably noise regardless of topic (a marketing address, a low-signal group chat) and some are reliably worth attention (your manager, a close collaborator) almost independent of what they're currently saying. Blend a lightweight per-sender trust prior — learned purely from your own feedback history, not hardcoded rules — into the final score.

**How it would work:**

- Maintain a simple running statistic per sender (e.g. mean llm_score and thumbs-up rate over their historical items) — a small aggregate query over the existing `items`/`feedback` tables grouped by `sender`, no new model needed to start.
- Blend this as a modest adjustment to the LLM's per-message score (e.g. a sender with a strong history of thumbs-down on high scores nudges future scores down slightly; a sender with a strong history of thumbs-up on notifications nudges up) rather than a hard override — content relevance should still dominate.
- This is a natural extension of the feedback-driven tuning already planned, just applied per-sender instead of globally.

**Open questions to resolve before building this:**

- How much history is needed per sender before the prior is trustworthy (avoid overreacting to one or two data points from a new sender)?
- Should this be visible/explainable in the dashboard (e.g. "score adjusted down: this sender's messages are usually not relevant") so it doesn't feel like an opaque black box?
- Risk of the prior becoming self-fulfilling — if a sender's messages start getting suppressed, you get less chance to give feedback on them, potentially entrenching an early wrong impression.

## Alternate form: Browser extension

**The idea:** instead of (or alongside) the React dashboard, ship Signal Filter's frontend as a browser extension. This isn't a rewrite — the Python backend (Slack/Gmail connectors, Ollama, Postgres, the FastAPI API) keeps running locally exactly as it does today; an extension is just a different client hitting the same `localhost:8000` API the dashboard already talks to. Two distinct versions worth building, in order of ambition:

1. **Popup/side-panel dashboard** — the simplest version: the extension's popup (or a persistent side panel, which Chrome/Edge support via the Side Panel API) fetches `/items` and `/focus` the same way `App.tsx` does now, showing Surfaced/Filtered right from the browser toolbar instead of a separate tab. Close to a direct port of the existing dashboard into an extension shell.
2. **Inline injection into Gmail/Slack's own web UI** — the more differentiated version, already noted as a long-term idea before this was written up in detail: a content script that reads the current Gmail/Slack web page and injects a relevance badge or highlight directly next to each message in the inbox/channel list, using scores already computed by the existing pipeline (matched up via `thread_id`/sender/content, or a new endpoint like `GET /items/by-thread/{thread_id}`). This means never needing to open a separate dashboard at all — the triage decision shows up right where the message already is.

**What doesn't change:** the extension is purely a frontend. It cannot host the Slack Socket Mode connection, the Gmail poller, Ollama, or Postgres — those need a long-running local process regardless, especially since Manifest V3 (the current Chrome extension platform) intentionally limits how long extension background scripts can run, ruling out hosting the actual pipeline inside the extension itself. The backend stays exactly as architected; this only adds a new way to see its output.

**How it would work, technically:**

- Manifest V3 extension, `host_permissions` scoped to `http://localhost:8000/*` so it's allowed to call the local API from a content script or popup (Chrome blocks arbitrary localhost fetches from web pages by default, but an extension with explicit permission is exempt).
- Reuse `frontend/src/api.ts`'s fetch wrappers largely as-is — the API surface doesn't need to change for the popup version.
- For inline injection: a content script matching `mail.google.com` / `app.slack.com`, using `MutationObserver` to catch Gmail's/Slack's dynamically-rendered message lists (both are heavy SPAs, so this can't rely on a static DOM), matching each visible message to its `Item` row and rendering a small badge (color-coded by score, tooltip with the LLM's reason) without altering the site's own functionality.

**Open questions to resolve before building this:**

- Gmail and Slack's web UIs are both unstable/obfuscated DOM targets that change over time — a content script matching their internals is inherently more fragile than the connectors talking to their official APIs, and would need ongoing maintenance as their frontends change.
- Does the popup version replace the standalone dashboard, or do both coexist (dashboard for a fuller view, extension for at-a-glance/inline)?
- CORS is already handled for `localhost` broadly (see the dashboard's CORS fix) — an extension's origin (`chrome-extension://...`) would need to be added to the allowed origins too.
- Packaging/distribution: purely a local unlisted extension (load unpacked, or a private Chrome Web Store listing), since this is a personal tool reading personal data — not intended for public distribution as-is.
